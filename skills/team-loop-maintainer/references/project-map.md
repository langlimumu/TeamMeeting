## Domain invariants

- A user owns one member profile; inactive users disappear from current member views while history remains.
- Member drag ordering accepts exactly the active participating members visible in the selected organization route; the server must not validate against or return the global member set.
- User management supports client-side account/name/employee-ID search, organization/type/auth filters, and transaction-safe bulk type, organization, or soft-delete operations. Bulk deletion must protect the current account, revoke sessions, and create one recycle record per user.
- Guest modules are selected through the reserved `guest` permission template; the frontend consumes `/api/me` and must not maintain a separate allowlist.
- User-type permissions include view/create/edit/delete; UI hiding never replaces server checks.
- User-type participation scopes independently control current team-member, morning, red/black, and Thank You candidate lists without deleting history.
- Organization visibility controls which users and organization-owned records are in scope; it is independent from module permissions and participation scopes. Client organization paths must always be intersected with the authenticated user's accessible organization IDs.
- Organization propagation separates the selected organization, broader visible routes, and ancestors. Morning, shifts, attendance, red/black, and Thank You use direct members of the selected organization; only meetings and announcement topics inherit from ancestors.
- User types are dynamic. Only `guest` is reserved; it is read-only and cannot be assigned to an account.
- Past morning-meeting dates are read-only; unfinished items inherit through a root chain.
- Completed or archived meetings lock agenda and minutes until an admin reopens them.
- Meeting creation follows the `meetings.create` operation permission; only administrators maintain first-level topic categories and second-level presets.
- Meeting presets are batch-added through `/api/meetings/{id}/agenda-options`, with an optional owner per selected item; `meetings.start_time` is `HH:MM` or empty.
- Process templates belong to an organization and inherit downward read-only. Templates are forests with parallel roots and tree branches, and the editor mind map is derived from ordered parent keys rather than stored coordinates. Creating an instance snapshots every node and parent relation; later template edits or deactivation must not mutate existing instances. Children require completed parents, parent resets cascade downward, and required nodes determine automatic completion.
- Team discussion is a forum-style topic list with categories, search, sorting, pagination, detail replies, soft deletion, and recycle restore. Authors manage their own topics; only administrators publish announcements or pin topics.
- Discussion Emoji picker code, locale, and Emoji data are local static assets and must work without public internet access.
- Public domains terminate TLS in local Nginx and proxy to a loopback Team Loop port. Forwarded IP/protocol are trusted only from loopback when explicitly enabled.
- Red and black scores remain separate; do not silently convert to a net score.
- Black-score summary and detail visibility are separate system settings; non-admin API responses must be filtered server-side while administrators retain full management access.
- A user may edit/delete only allowed Thank You records; weekly recipient limits come from settings.
- Link edits and deletes are available to users whose type grants the matching operation, with soft deletion and audit history.
- OAuth2 manual configuration groups the authorization, access-token and UserInfo endpoints with Client ID and callback guidance. Client Secret is write-only in the UI and may be supplied with `TEAM_LOOP_SSO_CLIENT_SECRET`; public settings expose only readiness, auto-login state and button text. Employee ID is the user-management link, external subject is the stable provider identity, and the deepest matching SSO group selects the organization route.
- Gray uses a production snapshot and never writes its test data back to production.
- Team norms are crowd-recorded and organization-scoped, and each category owns its **own document** instead of being a chapter of one big file: `GET /api/norms/document` returns a `documents` array with one entry per category (`category_id`, `parent_id`, `parent_name`, `level`, `child_count`, `name`, `title`, `article_count`, a single-element `chapters`, and its own `markdown`). Article numbers are **per document** (`1`, `2`, `3`, restarting in every document) with no category prefix, because a category's ordinal comes from `sort_order` and prefixing would renumber every document whenever categories are reordered; cross-document references name the document, e.g. 「见《研发流程规范》第 2 条」. Only `active` and unexpired norms enter a document; empty categories keep an empty document so the navigation mirrors the shelves and a freshly created category never disappears. There is deliberately **no versioning** — a document is a live projection of `norms`, so recording or editing renumbers it immediately. `norm_doc_versions` is still created but nothing reads or writes it: do not reintroduce a publish/preview flow without also reintroducing a frozen release view, because rendering live content under a version label was the original bug. Category deletion or deactivation is blocked while entries remain, and a norm may be edited by its author plus administrators.
- Norm categories are a **two-level tree** (`norm_categories.parent_id`, `NULL` = top level) and both levels hold norms directly, so 「研发流程」 and its sub-shelf 「python研发流程」 each own a separate document. A parent document shows **only its own clauses** — `parent_id` drives navigation indentation and the admin list grouping, nothing else; never make a parent document aggregate its children without asking, the independence is the point. Duplicate names are scoped per parent (`UNIQUE(org_unit_id, COALESCE(parent_id, 0), name)`), so two different top-level shelves may each hold a 「python研发流程」; that is also why the old org-wide unique index `idx_norm_categories_unit_name` is dropped and rebuilt on startup. The depth limit is 2 and is enforced on write (`resolve_norm_parent` rejects a parent that is itself a child, and rejects attaching a shelf with children): if you ever add a third level, the navigation tree, the `level` field and this guard all have to move together. A top-level shelf with sub-shelves cannot be deleted or deactivated until the sub-shelves are moved or removed. `list_norm_categories` stays a **flat** array but returns tree order (`ORDER BY COALESCE(p.sort_order, c.sort_order), c.parent_id IS NOT NULL, c.sort_order, c.id`) plus `child_count`, so the client can rebuild the nesting from `parent_id` alone; keep that ordering if you touch the query, or the indented navigation and the category `<select>` labels will interleave parents and children.
- Norm body text supports Markdown links `[label](https://…)` and bare `https://…` URLs. The client renders them through `formatNormContent()`, which escapes first and only accepts `http`/`https`, so unsupported schemes (`javascript:`) degrade to plain text; the stored string is untouched, which keeps the exported `.md` a standard Markdown link. Add link syntax support by extending that one pattern — do not switch the body to `innerHTML` with raw content.
- Norm **categories** have their own ownership-based permission tier, three levels deep in the sense of who may do what: everyone (including guests) reads; any signed-in user whose type has `norms` `can_create` may **create** both top-level and sub-shelves; **rename** and **delete** are both limited to the creator plus administrators; **reparent / deactivate** stays admin-only. Ownership lives in `norm_categories.created_by` (guests and system-seeded shelves have `NULL`, meaning "shared, admin-only delete"). Two implementation details are load-bearing: (a) the route layer remaps `DELETE /api/norm-categories/{id}` to the module `edit` action, because the coarse `module_permissions` table cannot express "same user type, but only your own records" — the real check is `can_delete_norm_category(category, user)` inside the handler; do not "simplify" it back to the module `can_delete`, that either blocks every member or lets them delete each other's shelves. (b) `can_delete` and `can_rename` are computed server-side and shipped on every category row and every document in `GET /api/norms/document`, so the frontend only draws a button / lets a double-click through and never re-implements the rule; `can_rename_norm_category()` deliberately delegates to `can_delete_norm_category()` so the two rules cannot drift. One deliberate exception: the admin "preview as type" mode is **client-side only** (the server still resolves the real admin and returns `can_delete: true`), and ownership cannot be derived from a *user type*, so `canDeleteNormCategory()` and `canRenameNormCategory()` return `false` outright whenever `state.permissionPreview` is set — the admin loses the extra `×` and the rename shortcut in preview on purpose, while `＋` still follows the previewed type's `create` permission. Do not "fix" that by trusting the server flag again. The create / delete controls live on the **left** directory nav (`#normDocNav`) as a `＋` per top-level row and a `×` per deletable row, both **siblings** inside the row grid (a `<button>` cannot nest a `<button>`), plus one create modal (`#normCategoryModal`, create-only, reused for both levels via a hidden `parent_id`). **Renaming has no button at all**: it is a *double-click on the shelf name*, which swaps that grid cell for an `<input class="norm-nav-input">` (the whole `.norm-nav-item` button is replaced, because an `<input>` is interactive and cannot live inside a `<button>` either). Two traps are baked into that: (1) do **not** listen for the native `dblclick` event — the first click calls `renderNormNav()` and rebuilds the list, so the second click lands on a *new* node and no `dblclick` is ever fired; `normNavClickIsDouble()` compares `state.normNavLastClick` timestamps (500 ms window) instead. (2) the input is re-created on every re-render, so `commitNormRename()` bails out when the element's `data-norm-rename-key` no longer matches `state.normRenamingKey` (a stale node would otherwise PATCH its text onto a *different* shelf) and clears the state *before* awaiting, which is what stops the post-Enter `focusout` from submitting twice. Enter saves, `Escape` cancels, `focusout` saves; `renameNormCategory()` sends **only** `name` (no `parent_id` / `active` — a non-admin sending those gets a 403, refused rather than silently ignored; no `description` either, so the server keeps the stored one) and deliberately does **not** touch `state.normActiveCategory`, because the user has usually already clicked another shelf while the PATCH was in flight. The right-hand management panel is admin-only and keeps the full form (rename / reparent / deactivate); `update_norm_category` keeps the stored description when the field is absent, so a rename cannot blank it. When touching the nav, remember `syncNormWritePermissions()` hides the root-create button and the panel per `can_create`, the row grid `20px minmax(0,1fr) auto` needs the `.norm-doc-body` first column to stay at **236px** for a row carrying up to two 20px buttons (the rename input lives in that same `minmax(0,1fr)` cell, so it inherits the width), and every new `button` **and `input`** needs the `body[data-theme] X` pair or the miro/dingtalk theme rule repaints it.
- The team-norms page has **no separate entry list** — the document is the only place clauses are read *and* edited. Each article therefore ships `status` (to fill the edit form) and `can_edit`, computed by `can_edit_norm()` — the same function `update_norm` enforces (author plus administrators). The client draws 「编辑」 from that flag and never re-derives ownership; as with `can_delete` on shelves, 「preview as type」 forces it to `false` because ownership is per-person and cannot follow a *user type*. 「删除」 on an article is module-level only (`norms` `can_delete`, `0` for the default member type, so admins only) — `delete_norm` has no ownership check of its own. Picking a shelf on the left also drives the right-hand create form's category via `syncNormCreateCategory()`, which is skipped while `state.editingNormId` is set so an edit target can never be silently moved to another shelf. Consequence worth knowing before touching this: `pending` / `abolished` clauses leave the document by design, so with the list gone there is no longer any UI path back (the rows survive; `PATCH /api/norms/{id}` restores `status`). If the team wants "hide it and dig it out later", add an `include_abolished` switch to the document endpoint rather than resurrecting the list.
- Norm body illustrations are stored as **files, not BLOB columns**: `norm_images` holds only a relative `stored_path`, and the bytes live under `UPLOAD_DIR` (`data/uploads/norms/YYYY/MM/`, random UUID names, month-sharded so no directory grows unbounded). The reason is the deploy path, not taste — `scripts/db_snapshot.py` copies the entire database page by page through `sqlite3.backup()` and then runs `PRAGMA integrity_check`, and `deploy.ps1` takes that snapshot **twice** per release (gray copies the production database, promote backs it up) plus once more on rollback, so binary data in the database makes every release cost grow linearly with image count and fills `data/backups/` with full-size copies. `data/` is also the only directory both deploy flows exclude (`robocopy /MIR /XD data`; the release snapshot copies only `server.py`, `team_loop`, `static`, `previews`), so anything user-uploaded that lands elsewhere gets frozen into a release or deleted by the mirror. Never serve these through `serve_static`: it performs **no auth at all** and hardcodes `Cache-Control: no-store`, so illustrations have their own `GET /api/norm-images/{id}` route that reuses the module gate plus the organization-scope filter, answers 404 (not 500) on a non-numeric id, and caches with `?v=` versioning.
- A clause references an illustration by **server-issued integer id only** — `[[img:12]]`, never a URL or HTML. `formatNormContent()` matches that marker in the same single pass as links and resolves it against the `images` array the server ships with each article; an id missing from that array renders a 「图片已移除」 note instead of a broken image. This is what keeps the body renderable without `innerHTML`, and it is also what makes the storage backend swappable — do not start storing paths in the body. Uploading only **stages** a row (`norm_id` NULL); saving the clause binds the ids present in the body and releases the ones that disappeared (`bind_norm_images`), and a release must stay reversible because the image is not deleted — `sweep_staged_norm_images` collects whatever is still unreferenced after 24 hours, opportunistically on the next upload rather than on a timer. The whitelist is JPG/PNG/WebP validated against the **file signature**, not `Content-Type`, and SVG is deliberately excluded because an image is served to the browser as a document while SVG can carry script. The client downscales to a 1600px long edge (WebP) before uploading, which is where most size control actually happens.

## High-risk areas

- `server.py` is a compatibility entry point. Domain code belongs in `team_loop/`; route ordering in `handlers/request.py` can still shadow dynamic paths.
- SQLite supports concurrent reads through WAL but serializes writes. Keep databases on local disks, preserve bounded HTTP workers, and run the 100-request concurrency smoke test after connection or transaction changes.
- `static/app.js` renders HTML strings; missing `escapeHtml()` creates stored-XSS risk.
- Sessions are persisted as token hashes in SQLite; authentication changes must preserve expiry, revocation, device listing, and login throttling.
- User types and morning items use optimistic versions; stale writes must return 409 instead of overwriting newer data.
- Shift batches are atomic and must reject duplicates or daily-hour conflicts before inserting any row.
- SQLite files cannot be replaced while another Windows process holds them open.
- Theme-specific CSS appears after base CSS and can override new styles.
- Development hot reload on port 8000 may point at the main database; use Gray for destructive tests.
- A live instance only picks up part of an edit: `static/*` is re-read from disk on every request, but Python modules are imported once at process start, so a page can show a **new frontend with an old backend** (e.g. neutral navigation without sequence numbers, yet article numbers still coming from the stale `no`). Edits under `team_loop/` require restarting the process; "the fix is not visible" almost always means a process started before the edit, not a broken change.
- Before trusting a screenshot or reporting a bug, identify which release actually serves the port: `data/deploy/runtime/production.json` records `release`, `release_path`, `database`, `pid` and `started_at`, and the pid must match the process listening on that port. A `data/deploy/releases/<stamp>` snapshot is frozen at deploy time and can be days behind the working tree, and a deployment directory (`companytest/TeamMeeting-main`) carries its own `data/deploy` tree — a listener on `0.0.0.0:8000` may belong to a completely different copy of the project than the one being edited.
